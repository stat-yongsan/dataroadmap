# Jev: 확률로 다음 작업을 고르는 AI

60분 발표안 · 수학과 통계 기초 · 파이썬 실습 · 엑셀 자동화 적용

작성 기준: 2026-09-26. 대상은 확률 기초를 처음 배우는 대학 AI 동아리·업무 자동화 입문자다. 아래 20개 발표 단위는 각각 3분이다. 설명뿐 아니라 질문, 코드 실행, 결과 확인 시간을 포함한다. 이 문서는 슬라이드에 옮길 핵심 문장과 발표자 설명을 담은 발표 원고이며 PPTX 파일은 아니다.

## 먼저 확인한 사실

이 자료에서 Jev는 **TypeSafe AI의 System One 판단 모델**을 뜻한다. 공식 인터페이스는 `state`와 `questions`를 받고, **Choice·Score·Noul**에 맞는 구조화된 결과를 반환한다.[S1–S5]

사용자가 참고로 제시한 상태·행동·전이확률은 MDP와 강화학습에서 쓰는 개념이다. `E[R] − β Var(R)`는 평균과 변동성을 함께 고려하는 의사결정 목적함수로 해석할 수 있다. **이를 Jev의 공식 학습 손실이나 기본 출력 구조로 확인하지는 못했다.** 따라서 이 발표는 실제 Jev 인터페이스와, 그 출력으로 우리 프로그램에서 설계하는 의사결정 규칙을 나누어 설명한다.[S6, S11]

첨부 원본은 `Excel_Automation_Playbook_KO(1).md`다. 17개 영역, 153개 실습 카드, W01~W20 조합 프로젝트를 기준으로 사용했다. 153은 이 가이드의 설계 개수이며 모든 엑셀 업무의 수학적 최소 개수가 아니다. 카드가 존재한다고 실행 코드가 구현되어 있는 것도 아니다.

## 1. Jev의 역할 / 00–03분

**화면 문장**: Jev는 현재 상황에 대해 미리 정의한 질문에 답한다. 프로그램은 그 답을 사용해 다음 작업을 선택한다.

발표자 설명:

“교과·비교과 지출 파일을 받았다고 해 봅시다. 당장 합계를 내야 할까요? 금액이 `1,200원`이라는 글자로 저장되어 있다면 숫자로 바꾸는 작업이 먼저입니다. Jev에게 현재 자료와 작업 후보를 보여 주고, 지금 필요한 작업을 고르게 할 수 있습니다. 실제로 1,200과 800을 더하는 일은 파이썬이 합니다.”

이 예제의 역할은 다음과 같다.

| 구성요소 | 맡는 일 |
|---|---|
| 파일 분석 코드 | 열·자료형·행 수·오류를 실제로 확인 |
| Jev | 명시한 질문에 대해 선택·수준·참 여부를 평가 |
| 정책 코드 | 가능한 작업과 중단 조건을 검사 |
| 실행 코드 | 변환·연결·집계·차트 작업 수행 |
| 설명 템플릿 또는 생성 모델 | 결과를 사람이 읽을 문장으로 설명 |

청중 질문: “금액의 합계를 구하는 일과 어떤 계산을 할지 고르는 일은 어디에 맡기면 좋을까요?”

## 2. 참고 수식을 정확한 자리에 놓기 / 03–06분

| 참고 내용 | 실제 의미 | Jev 활용과의 연결 |
|---|---|---|
| 상태 s_t | 시점 t에서 알고 있는 상황 | `state`에 관련 자료와 작업 이력을 넣을 수 있음 |
| 행동 a_t | 선택한 작업 | Choice의 옵션을 실행할 함수에 연결 가능 |
| P(s_(t+1) \| s_t,a_t) | 행동 후 상태에 대한 전이 모형 | Jev가 기본 API에서 이것을 자동 제공한다고 볼 근거는 없음 |
| E[R] − β Var(R) | 보상의 평균과 변동성을 함께 고려 | 별도의 보상·확률 정의가 있을 때 정책 코드에서 계산 가능 |
| ‘두 가지 함수를 출력’ | 참고 문장에 함수 정의가 빠져 있음 | 실제 공식 출력은 세 가지 질문 형식으로 확인됨 |

“참고 설명의 통계 개념은 활용할 수 있습니다. 다만 발표에서는 ‘Jev는 평균과 분산 두 함수를 출력하는 모델’이라고 소개하지 않겠습니다. API로 확인되는 동작과 응용 프로그램의 설계를 구분하겠습니다.”

Jev를 Joint Expected Value 같은 풀네임으로 임의 확장하지 않는다. System One은 공급자가 사용하는 모델 계열 명칭이며 인간의 사고체계를 완전히 재현했다는 증명은 아니다.

## 3. 상태는 판단에 필요한 정보 / 06–09분

가상 입력:

| 부서 | 금액 |
|---|---|
| 교과 | 1,200원 |
| 교과 | 800원 |
| 비교과 | 500원 |

상태에는 원자료만 넣기보다 필요한 맥락을 함께 넣는다.

```json
{
  "goal": "부서별 금액 합계",
  "grain": "거래 1건",
  "amount_unit": "KRW",
  "amount_type": "통화 문자가 포함된 문자열",
  "completed_steps": [],
  "available_steps": ["C03", "I01", "N02"]
}
```

“똑같은 엑셀이라도 ‘돈의 합계’가 목표인지 ‘참여자 수’가 목표인지에 따라 필요한 작업이 다릅니다. 한 행이 학생 한 명인지 신청 한 건인지도 중요합니다. 모델이 추측해야 할 것을 줄이는 것이 상태 설계입니다.”

API의 state는 컨텍스트 입력이다. 기본 호출에서 지난 요청을 자동으로 기억한다고 가정하지 않는다. 다음 판단에 필요한 이력은 프로그램이 저장하고 다시 전달한다.[S7]

## 4. 확률변수와 확률분포 / 09–12분

확률변수 Y는 아직 확정하지 못한 결과를 표현한다. ‘다음에 필요한 작업’처럼 범주일 수도 있고 ‘얻게 될 점수’처럼 수치일 수도 있다.

아래는 **실제 Jev 응답이 아닌 교육용 예시**다.

| 다음 작업 Y | 확률 |
|---|---:|
| C03 문자 숫자 정리 | 0.70 |
| D03 중복 검출 | 0.20 |
| I01 그룹 집계 | 0.10 |
| 합계 | 1.00 |

각 확률은 0~1이고, 서로 배타적인 선택지를 모두 포함한 한 분포의 확률 합은 1이다. 0.70은 70%와 같다.

여기서 C03의 번호 3과 D03의 번호 3을 평균 내는 것은 의미가 없다. **선택지 이름은 명목척도**다. 뒤에서 보는 Score는 순서가 정의된 수준을 사용하므로 수준 번호의 가중평균을 계산할 수 있다.

청중 질문: “이 분포만 보고 I01이 절대로 필요 없다고 말할 수 있나요?” 답: 지금 가장 먼저 할 작업에 대한 평가와 전체 과정에서 필요한 작업은 다르다.

## 5. 조건부확률 / 12–15분

다음 기호는 API 계약을 설명하기 위한 개념적 표기다. 모델 내부 구조의 공식 방정식이라고 주장하지 않는다.

`p_k = Pθ(Y=k | state, question, criteria)`

- θ: 이미 학습된 모델의 매개변수
- Y=k: 답이 k번째 선택지인 사건
- 세로줄 `|`: 오른쪽 정보를 알고 있다는 조건
- criteria: 이번 판단에 제공한 선택지와 설명

“금액이 문자열이라는 조건에서는 정리가 먼저일 수 있습니다. 숫자로 바뀌었다는 새 조건에서는 집계가 먼저일 수 있습니다. 상태가 바뀌면 같은 질문에도 답이 바뀝니다.”

Choice에서 C03의 확률이 0.7이라는 것과 C03 프로그램의 실행 성공 확률이 0.7이라는 것은 다르다. 질문이 ‘가장 적절한 다음 작업’이면 그 답의 적절성을 평가한다. 실행 성공률을 알려면 실행 이력과 성공 기준에 관한 별도 증거가 필요하다.

## 6. 기댓값과 분산 / 15–18분

기댓값은 ‘각 결과에 확률을 곱해 모두 더한 값’이다.

`μ = E[X] = Σ p_i x_i`

분산은 ‘결과가 평균에서 얼마나 떨어져 있는지 제곱해서 확률로 평균 낸 값’이다.

`σ² = Var(X) = Σ p_i (x_i − μ)²`

| 방식 | 결과 분포 | 기댓값 | 분산 |
|---|---|---:|---:|
| 안정형 A | 항상 6점 | 6 | 0 |
| 변동형 B | 0점 또는 14점, 각각 50% | 7 | 49 |

B의 계산은 `0×0.5 + 14×0.5 = 7`, 분산은 `0.5×(0−7)² + 0.5×(14−7)² = 49`다.

“평균만 보면 B가 좋습니다. 하지만 B는 어떤 때 0점입니다. 결과의 흔들림도 고려하려면 분산 같은 값을 함께 봅니다.”

분산의 단위는 점수²다. 표준편차는 분산의 제곱근이므로 B의 표준편차는 7점이다. 분산은 좋은 방향의 큰 변화도 함께 벌점으로 센다. 큰 실패만 특별히 다루려면 별도의 손실함수나 제약이 필요하다.

## 7. Choice와 Noul / 18–21분

**Choice**는 미리 정한 선택지 중 하나를 고른다. 공식 응답에는 최대 확률의 `choice`, 전체 `probabilities`, 그리고 분포를 요약한 `confidence`가 있다.[S2]

예: “가장 먼저 다룰 영역은 구조 해석, 표준화, 집계 중 무엇인가?”

**Noul**은 예/아니오 질문에서 예일 확률을 준다. 예: “사용자가 집계 기준을 명시했는가?” `noul=0.8`은 그 질문에 예라고 판단할 확률이다. 별도의 confidence 필드는 없다.[S4]

여러 문제가 동시에 존재하면 영역마다 별도의 Noul을 묻는 방식이 알맞다. 표준화 필요와 중복 검토 필요가 둘 다 참일 수 있다. 이 값들을 더해서 1로 만들 필요는 없다.

한 번의 호출에 독립적으로 답할 수 있는 여러 질문을 묶을 수 있다. 그러나 **API가 질문을 별도로 평가한다는 사실은 실제 사건들이 통계적으로 독립이라는 뜻이 아니다.**

## 8. Score와 기댓값 / 21–24분

집계 준비도를 다음 세 수준으로 정했다고 하자.

| 수준 번호 | 구체적인 상태 | 교육용 확률 |
|---:|---|---:|
| 0 | 필수 열이 없음 | 0.10 |
| 1 | 열은 있으나 문자 숫자를 정리해야 함 | 0.70 |
| 2 | 숫자형 열이 준비되어 집계 가능 | 0.20 |

`Score = 0×0.10 + 1×0.70 + 2×0.20 = 1.10`

공식 Score는 수준 번호의 확률 가중평균이다. 1.10은 정답률 110%도, 준비가 55% 완료되었다는 측정값도 아니다. 설정한 수준 사이에서의 위치다.[S3]

같은 평균의 다른 분포:

| 분포 | Score | 수준 번호의 분산 |
|---|---:|---:|
| 0%, 100%, 0% | 1 | 0 |
| 50%, 0%, 50% | 1 | 1 |

수준 번호의 간격은 우리가 정한다. 점수 2가 점수 1의 두 배 가치라는 뜻은 아니다. 정확한 금액·날짜를 Score로 보간해서 계산하지 않는다.

## 9. 정확도, 보정, confidence / 24–27분

정확도는 “선택한 답을 얼마나 자주 맞혔는가”다. 보정(calibration)은 “80%라고 예측한 사건들이 실제로 약 80% 일어나는가”다. 많은 사례를 묶어 확인하는 성질이다.[S6, S10]

아주 작은 설명용 예로 예라고 예측한 10건 중 실제 예가 8건이라고 하자. 모든 사례에 확률 0.8을 준 모델과 0.99를 준 모델은 0.5 임계값에서 같은 80% 정확도를 보인다. 그러나 이 집합에서 0.99는 과도한 확신이다.

이진 Brier 점수:

`Brier = (1/N) Σ (p_i − y_i)²`, `y_i ∈ {0,1}`. 작을수록 좋다.

- 모두 0.8이라고 예측: `(8×0.2² + 2×0.8²)/10 = 0.16`
- 모두 0.99라고 예측: `(8×0.01² + 2×0.99²)/10 = 0.1961`

이 예제는 실제 성능 평가가 아니다. 전체 비율을 항상 답하는 모델도 보정되어 보일 수 있으므로 판별력, 작업 비용, 자동처리율을 함께 본다. Brier도 보정만 단독 측정하는 지표는 아니다.

**Jev의 confidence는 응답 확률분포를 요약한 통계량이다.** `confidence=0.9`를 ‘실제 정답률 90%’라고 읽지 않는다. 최대 확률이나 엔트로피와 같은 공식이라고 임의 정의하지 않는다.[S5]

## 10. RLCD와 공개된 범위 / 27–30분

TypeSafe는 학습 방식을 **Reinforcement Learning for Calibrated Decisions**, 줄여서 RLCD라고 설명한다. 판단과 확률을 잘 반환하도록 학습한다는 방향이다.[S6]

청중에게는 이렇게 말할 수 있다.

“시험에서 답만 잘 고르는 능력과, 내가 얼마나 확신하는지 정확하게 표현하는 능력을 함께 생각해 봅시다. 모르는 문제에도 무조건 100%를 말하면 자동화 프로그램이 잘못된 결정을 내릴 수 있습니다.”

공개 자료에서 확인한 범위와 설명용 도구를 구분한다.

| 구분 | 발표에서 말할 내용 |
|---|---|
| 확인한 제품 동작 | 세 가지 질문 형식, 구조화된 응답, 확률분포 |
| 공급자의 학습 설명 | RLCD를 통한 보정된 판단 지향 |
| 교육용 통계 설명 | Brier, 기댓값, 분산, 엔트로피 |
| 이 자료에서 확인하지 못한 것 | 정확한 전체 학습 손실, 상세 아키텍처, 재현 가능한 전체 학습 절차 |

따라서 “Jev는 Brier 하나로 학습한다” 또는 “Jev의 공식 손실은 평균−분산이다”라고 단정하지 않는다. 실제 업무 적용에서도 높은 confidence는 정답 보증이 아니다.

## 11. 상태·행동·전이·정책 / 30–33분

| 개념 | 이 실습에서의 예 |
|---|---|
| s₀ | 금액이 문자열인 거래 표 |
| a₀ | C03 문자 숫자 변환 |
| s₁ | 금액이 숫자로 바뀐 거래 표 |
| a₁ | I01 부서별 합계 |
| s₂ | 부서별 집계표 |
| 정책 π | 상태와 판단을 보고 다음 허용 작업을 선택하는 규칙 |

이 앱에서는 실제 실행 코드와 그 결과 검증이 전이를 만든다. 구조를 `s_(t+1)=T(s_t,a_t,실행 결과)`로 표현할 수 있다. 업무 규칙과 입력이 확정된 계산은 대부분 결정적이다. 파일 오류나 외부 서비스 실패는 별도로 관측하고 처리한다.

MDP는 현재 상태가 미래 판단에 필요한 정보를 담는다고 가정한다. 실제 업무에서는 규칙·키·목표를 모르는 일이 많으므로 충분한 정보가 있는지 점검해야 한다. 단순히 API에 state라는 필드가 있다고 완전한 MDP가 되는 것은 아니다.

**여러 단계로 Jev를 호출하는 것만으로 모델이 온라인 강화학습을 하는 것은 아니다.** 저장한 이력으로 프로그램의 상태를 갱신하는 것과 모델 가중치를 다시 학습하는 것은 별개다.

## 12. 사용자가 제시한 위험 조정 수식 / 33–36분

한 번의 선택을 평가한다면 다음처럼 쓸 수 있다.

`U(a | s) = E[R | s,a] − β Var(R | s,a)`

`a* = argmax_a U(a | s)`

| β | A의 효용 | B의 효용 | 선택 |
|---:|---:|---:|---|
| 0 | 6 | 7 | B |
| 0.01 | 6 | 6.51 | B |
| 0.05 | 6 | 4.55 | A |

β가 클수록 변동성에 큰 벌점을 준다. 두 선택은 β=1/49에서 같아진다. 보상을 점수에서 100배 큰 단위로 바꾸면 같은 β를 그대로 사용할 수 없다. 이때 등가의 순위를 유지하려면 β도 1/100로 바꾸어야 한다.

다단계 정책을 최적화하려면 보통 누적 보상 `G=Σ γ^t r_t`를 먼저 정의하고 `max_π {E_π[G] − β Var_π(G)}` 같은 목적을 생각한다. 매 단계의 평균−분산을 탐욕적으로 최대화하는 것이 전체 경로의 이 목적을 최대화한다고 보장되지 않는다. 평균·분산을 다루는 MDP는 별도 연구 주제다.[S11]

엑셀 MVP는 먼저 **허용 조건과 오류 비용에 따른 규칙**으로 구현하는 편이 검증하기 쉽다. 보상 분포의 근거 없이 Choice 확률을 보상 확률로 바꾸거나, 장기 최적 정책이라고 주장하지 않는다.

## 13. 통계 실습 실행 / 36–39분

다운로드한 폴더에서 Windows 터미널 또는 VS Code 터미널을 연다.

```powershell
py -3 jev_stats_demo.py
```

`py`가 없는 환경에서는 다음을 쓴다.

```text
python jev_stats_demo.py
```

외부 패키지, API 키, 인터넷이 필요 없다. 실습은 평균·분산, 같은 평균의 다른 Score 분포, 작은 Brier 예제, 오류 비용에 따른 검토 선택을 출력한다.

손으로 바꿔볼 값: B의 좋은 결과 14를 16으로 바꾼다. 이제 B의 평균은 8, 분산은 64다. β=0.05에서 B의 효용은 4.8이므로 여전히 A가 선택된다.

발표자가 짚을 점: 이 프로그램은 확률을 학습하지 않는다. 우리가 정한 확률에서 통계량을 계산한다.

## 14. Jev 판단과 Python 실행 / 39–42분

먼저 확실히 재현되는 예시를 실행한다.

```powershell
py -3 jev_easy_demo.py
```

이 모드는 `MOCK`이라고 표시한다. 고정된 교육용 응답을 사용하여 C03 실행, 상태 변경, I01 실행을 보여 준다.

실제 모델 실습은 다음과 같다.

```powershell
py -3 jev_easy_demo.py --live
```

키가 환경변수에 없으면 화면에 표시하지 않는 입력창에서 받는다. 실제 모드는 가상자료만 공식 API로 전송하며 최대 두 차례 호출한다. TypeSafe 계정·API 키·접근 가능한 네트워크와 서비스 이용 조건이 필요하다. Jev API 이용이 무료라고 전제하지 않는다. `JEV_MODEL`을 설정하지 않으면 확인한 공식 별칭 `jev-latest`를 사용하고 응답의 실제 모델명을 출력한다.[S8]

실행 흐름:

1. 첫 요청에서 Jev가 현재 상태를 보고 C03을 선택하는지 확인한다.
2. Python이 ‘1,200원’을 정수 1200으로 바꾼다.
3. 숫자로 바뀐 행과 성공 이력을 다음 state로 보낸다.
4. Jev가 I01을 선택하면 Python이 교과 2000, 비교과 500을 계산한다.

실제 모델이 다른 답을 하거나 예시 임계값을 충족하지 못하면 `needs_review`로 멈춘다. 이를 모델의 답에 맞게 억지로 정답 처리하지 않는다. API 실패를 MOCK 성공으로 바꾸지도 않는다. 이 자료 작성 시 실제 인증 API 호출은 수행하지 않았다.

## 15. 파일 업로드 후 먼저 할 일 / 42–45분

업로드 파일을 처음에는 코드로 조사한다. 시트 이름, 표 후보, 자료형, 빈값, 가능한 키, 병합 범위, 수식 여부 등을 계산한다. 행수나 합계를 모델에게 세게 하지 않는다.[S9]

판단 상태에 포함할 핵심은 다음과 같다.

| 정보 | 이유 |
|---|---|
| 목적 또는 후보 목적 | 돈 합계·사람 수·변화 비교는 필요한 경로가 다름 |
| 한 행의 의미 | 학생 중복과 신청 중복을 구별 |
| 실제 프로파일링 결과 | 모델 추정치와 측정값을 구별 |
| 적용 가능한 작업 카드 | 정의된 작업 범위 안에서 판단 |
| 업무 규칙 | 분모·기간·단위·중복 정책을 임의로 만들지 않기 |
| 실행 환경 | Windows Excel이 필요한 기능의 실행 가능성 확인 |

목적이 비어 있으면 데이터가 지원하는 활용 시나리오 몇 개를 제안한다. 어떤 경로가 유일한 정답이라고 선언하지 않는다. 필수 업무 규칙이 부족하면 해당 실행은 검토 상태로 표시한다.

## 17. 같은 데이터에서 갈라지는 활용 경로 / 48–51분

예를 들어 신청번호·학번·부서·상태·신청일이 있는 가상 자료를 생각하자.

| 활용 목적 | 주요 경로 | 필요한 규칙 |
|---|---|---|
| 부서별 신청 건수 | 키 점검, I01 집계, N02 차트 | 한 행은 신청 1건 |
| 실제 참여자 수 | 식별자 보존, I02 distinct count, N02 | 여러 신청을 한 사람으로 셀지 |
| 인증률 | 검증, 신청·인증 건수 집계, H01, N02 | 분자·분모와 기간 |
| 월별 변화 | 날짜 정리, J01, J03, N02 | 기준 기간, 미수집과 0의 구별 |

가이드 W02의 가상 정답은 교과 30/60=50%, 비교과 10/40=25%, 전체 40/100=40%다. 두 부서 비율을 그냥 평균 낸 37.5%는 전체 인증률이 아니다.

사이트는 실제로 실행한 상태, 계획상 가능한 상태, 정보가 부족한 경로, 아직 구현하지 않은 작업을 서로 다르게 표시해야 한다. 실행 전에는 “중복이 0개가 될 것” 같은 결과를 확정하지 않는다.

## 18. 경로 탐색과 경우의 수 / 51–54분

매번 하나만 고르면 초기 판단이 틀렸을 때 다른 활용을 놓칠 수 있다. 후보 경로를 몇 개 유지하며 비교하는 **beam search**를 사용한다. 공식 Jev 문서에도 계층적 분류와 beam search 예제가 있다.[S12]

우리 설계는 여기에 각 작업의 입력·출력 계약을 추가한다. 분류가 끝나도 처리는 끝나지 않는다. 실제로 선택한 작업을 실행한 뒤 상태를 다시 조사하고 새 후보를 만든다.

| 표시 | 의미 |
|---|---|
| 선택지 확률 | 현재 질문의 선택지에 대한 모델 평가 |
| 경로 추천 점수 | 여러 단계의 값을 비교하기 위해 앱이 계산한 점수 |
| 실제 성공률 | 정의된 업무를 반복 실행해서 관측한 비율 |

이 세 값은 서로 다르다. 여러 단계의 Choice 확률을 곱했다고 자동으로 업무 성공률이 되지 않는다. 같은 상태에서 평가한 질문도 현실의 사건들이 독립이라는 뜻은 아니다.

깊이 6에서 매번 3개로 분기하면 끝 경로는 최대 3⁶=729개다. 실제로는 선행조건과 종료 상태가 가지를 줄인다. 화면에는 우선 상위 3개를 펼치고, 더 보기에서 확장한다. 표시된 경로는 설정한 탐색 범위 안의 후보이며 모든 가능성의 완전한 목록이 아니다.

## 19. 평가와 자동실행 조건 / 54–57분

먼저 원자료에서 확실히 계산할 수 있는 값을 검사한다. 모델이 ‘문제없음’을 골라도 코드가 중복 키나 미확정 분모를 찾으면 실행 규칙이 우선한다.

평가할 항목:

- 적절한 작업이 후보 안에 있는가: 후보 재현율, 단계별 정확도
- 예상 확률이 실제 결과와 맞는가: 정답 라벨과 보정 도표, Brier
- 자동으로 처리한 사례에서 오류는 얼마나 생겼는가: 자동처리율과 그 집합의 오류율
- 전체 결과는 맞는가: 행수·합계·중복·키·단위·정답 파일 대조
- 얼마나 드는가: 호출 수·토큰·응답 시간, 실제 모델 버전

임계값은 우리 업무의 오류 비용을 보고 조정한다. 실습 코드의 0.8 같은 값은 시작 예시다. confidence 하나만으로 실행 권한을 부여하지 않는다.

공식 한계 문서도 숫자 계산과 적대적 입력 등에 주의할 점을 설명한다. 따라서 업로드 셀의 문장을 명령으로 실행하지 않고, 모델이 고른 등록된 작업 ID만 검증 후 실행한다.[S9]

## 20. 마무리 질문 / 57–60분

| 질문 | 답 |
|---|---|
| Jev에게 엑셀 합계를 직접 맡길까? | 합계는 코드로 계산하고 Jev는 해석·선택에 사용한다 |
| Score 1.5가 정확도 75%인가? | 정의한 수준 번호의 가중평균이다 |
| confidence 0.9면 90% 맞는가? | 실제 라벨로 확인해야 하며 그 숫자만으로 보장되지 않는다 |
| API를 반복 호출하면 자동으로 학습되는가? | 상태를 갱신하는 것이며 모델 재학습과 별개다 |
| 파일만 있으면 유일한 최적 활용이 정해지는가? | 목표와 업무 규칙에 따라 여러 유효한 경로가 있다 |

마지막 활동: 본인 업무에서 “조건과 후보가 명확한 판단 하나”를 적는다. 예: 주관식 의견 범주 선택, 보고서 오류 검토 대상 선정, 사용할 자동화 카드 추천. 그 판단에 필요한 state와 가능한 답을 각각 적어 본다.

## 부록 A. 개발할 사이트의 핵심 반복

```text
현재 파일을 프로파일링한다.
목표와 업무 규칙을 상태에 넣는다.
선행조건을 충족하는 작업 후보를 만든다.
Jev가 관련성과 다음 작업을 평가한다.
정책 코드가 실행 가능 여부를 결정한다.
Python이 선택한 작업을 실행하고 결과를 검증한다.
새 상태를 저장하고 다음 판단을 한다.
종료·검토·지원 불가·실패 중 하나면 해당 경로를 멈춘다.
```

같은 state에서 독립적으로 답할 질문은 묶는다. 앞선 변환으로 데이터 자체가 바뀌거나 상세 카드 조회가 새로 필요하면 다음 호출로 나눈다. Jev가 반환하지 않는 장문 설명은 근거 템플릿 또는 별도의 생성 기능으로 제공한다.

| jev_stats_demo.py | 기댓값·분산·Brier·기대손실 실습 |
| jev_easy_demo.py | 고정 MOCK 또는 실제 Jev API로 2단계 판단 |

오프라인 계산과 MOCK 실행 결과를 확인한다. 실제 API 호출과 사이트 구현·배포는 이 자료 작성 작업에 포함하지 않았다. API 예제는 확인한 공식 HTTP 규격을 사용하며 실제 응답과 모델 버전은 실행 시 달라질 수 있다.

## 부록 C. 다른 업무에서의 활용

| 업무 | Jev에게 맡길 좁은 판단 | 코드 또는 다른 도구가 할 일 |
|---|---|---|
| 상담 문의 분류 | 환불·기술·이용안내 중 담당 경로 선택 | 티켓 저장, 담당자 배정 |
| Hermes 스킬 선택 | 요청과 맞는 후보 스킬 평가 | 필요한 스킬 문서를 읽고 실행 환경 준비 |
| 문서 검색 | 질문에 관련된 검색 결과인지 평가 | 원문 검색과 인용 위치 보존 |
| 비교과 자유의견 | 미리 정의한 개선 의견 범주 선택 | 집계, 검토 대상 표시, 보고서 작성 |
| 보고서 검수 | 근거가 주장을 뒷받침하는지 평가 | 수치·합계·분모의 정확한 계산 검증 |

위 표는 응용 설계 예시다. 한국어·우리 기관의 표현·카탈로그에서의 실제 품질은 별도 평가한다. TypeSafe의 [공식 스킬 추천 예제](https://docs.typesafe.ai/cookbooks/skill_suggestion)는 Hermes 스킬 후보를 평가하는 방법을 보여 준다.

## 출처

원문을 길게 인용하지 않고, 공식 인터페이스와 알려진 한계만 확인했다. 표의 가상 데이터, 설명용 확률, 임계값, 로드맵 설계는 이 자료의 교육·개발 예시다.

- [S4 Noul](https://docs.typesafe.ai/primitives/noul): 예/아니오 확률
- [S5 Confidence](https://docs.typesafe.ai/confidence): confidence의 의미
- [S6 AI primer](https://docs.typesafe.ai/introduction/machine-learning-primer): 공급자의 RLCD 설명
- [S7 State](https://docs.typesafe.ai/concepts/state): 입력 컨텍스트

- [S10 Guo 외, On Calibration of Modern Neural Networks, ICML 2017](https://proceedings.mlr.press/v70/guo17a.html): 확률 보정에 관한 연구

Jev 관련 추가 읽기: [Just Ask Jev, 2026-09-24 arXiv 제출](https://arxiv.org/abs/2609.29429). 정렬 실패 탐지 응용을 평가한 프리프린트다. 이를 Jev 내부 아키텍처 전체를 공개한 원전이나 모든 업무에서의 성능 보장으로 소개하지 않는다.
